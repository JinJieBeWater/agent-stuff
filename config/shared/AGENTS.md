这些是默认值，不是硬规则，我的偏好可以覆盖其中任何一条。规则和手上的任务冲突时，明确说出来，等我确认再破例。

先弄清真实约束，再选让正确行为不出意外的最小模型。复杂度不因已存在而保留，机制不为显得有架构感而加。量两次再切，同时 YAGNI：压住范围蔓延，用最小且现实的方式实现我的意图。

## 沟通

- 默认中文，代码、命令、路径、错误信息和 API 名称保留原文。先直接回答，再按需展开；agent 间交接已有长正文文件时，只回结论和路径。
- 向我提问时，同轮问题一次问完，每题单列；有选项时推荐项放首位，标「（建议）」并写明理由。

## 三种伤到自己的方式

1. **按模式杀进程。** 只结束启动时记下 PID 的进程，或确认 cwd 是本 worktree 的端口占用者。按名字、路径或 worktree 字符串去杀（`pkill -f`、`pgrep | kill`）会误伤你自己的 agent 进程和机器上其他 dev server。停后台任务用宿主自带的 stop，它会结束整个进程树。
2. **写正在使用的数据。** 测试要真实数据时复制一份进沙箱（复制，不软链），数据只单向流入。删除数据库或重置数据先得到我明确同意；删除用途不明的内容前先问。
3. **脱离会话的进程。** dev server 和构建从自己的 shell 启动，随会话结束；我要求常驻时才用 `nohup`、`setsid`、`tmux`、`systemd-run`。脱离的进程曾连跑数周，占满内存和 swap。

## 覆盖每个面

最常见的缺陷是改动在测过的那条路径上能用，别处全漏了。完成前逐项检查，并说明哪些适用：

- **入口**：同一行为的其他入口。
- **契约**：跨进程或网络的契约改了，所有消费方跟着改。
- **反向状态**：有进入就有退出和可见状态，单向门是 bug。
- **文档**：现有文档是否因此失真。

## 验证

- 测会坏的行为：编排、协议翻译、鉴权和权限守卫、持久化和迁移、外部格式解析、竞态修复、bug 修复改到的逻辑。类型已保证的、琐碎逻辑、文案、冒烟运行、mock 调用镜像、回调接线、静态渲染不测。
- 先扩展再新增：已有用例或表格覆盖到时，加一行或一个断言。只在一层测：在 main 上会失败的最低一层，不在包装层、各调用点或逻辑副本里重复。
- 浏览器测试只给需要真浏览器的行为：布局和滚动、焦点和指针输入、真 worker、接了 hooks 的组件。组件调用的逻辑写旁边的单元测试。
- 等待靠事件：await 标志里程碑的事件、promise 或队列项。需要 sleep、轮询、单测超时、`retry` 或 wall-clock 差值才能过的测试是错的，flaky 测试修好而不是重试。跳过的测试在上一行写跟踪 issue 和原因。
- bug 修复的证据按类型：逻辑、数据、状态、协议 bug 先写在 main 上失败的测试再修；纯视觉 bug（间距、颜色、对齐、布局跳动）用前后截图，不加测试；没有可见界面的服务端修复附测试和一段运行记录。
- 修复反馈时，完成标准是回放原始或同类场景并确认原错误消失；闪烁、跳动等动态问题逐帧比对过渡帧。测试和分数只作旁证。
- 用覆盖目标和实际风险的最小充分检查；仍然有效的结果直接复用，只补缺口。全仓检查交给 CI，我要求时才跑。
- 真实 agent turn 花钱：有免费的 replay 或 mock provider 就用；依赖真实 provider 行为时用它最便宜的模型。
- 审查默认 `ponytail-review`；同一范围只做一套完整审查，子 agent 遵循分配视角。仅在明确要求时做多 agent 独立复核。

## 提交与 PR

- 验证通过或没有可运行的验证时，自动按 Conventional Commits 提交，后者在交付中注明未验证；补修本任务的 HEAD 且确认未推送时 amend。push 由我发起；hook 失败时修根因后重新提交。
- 我明确要求时才开 PR。第一次用 forge 命令前看 `git remote get-url origin`，用对应 forge 的 CLI。标题用 Conventional Commits、白话；正文先用一两句写问题，再写修法，结尾写做这件事的模型和 harness。UI 改动附前后截图，动效附短视频，证据上传到 forge，不提交进仓库。一个请求一个 PR。
- 照看 PR 时：逐条对照源码核实 bot 的发现，修真的，误报写明理由驳回；没有新情况不发言；最新提交上 bot 全绿即停。

## 文档

- 多数代码改动不需要改内部文档。内部文档只写架构决策和理由、跨组件约束、读源码难发现的陷阱；读代码能回答的不写，不枚举功能、字段、控制流、文件清单或 PR 摘要。只在局部成立的理由写成旁边的短注释；跨边界的推理才进文档，并链接源码而不是复制。决策变了就改写或删掉原文，不追加新说法。
- 用户文档帮用户完成任务：每个主要功能一段，说清做什么、怎么开始、哪里反直觉；不描述可见的按钮、图标、布局和每种 UI 状态。
- 合并的 PR 就是实现记录，进度跟踪放在 issue 里，仓库里不留第二份清单。
- 计划、调研、反馈原文和 scratch 放仓库根目录的 `.workspace/`，不入库。worktree 里没有它时，照主 checkout（`git worktree list` 第一行）的 `.workspace` 建一个指向同一目录的软链；仓库没有 `.workspace` 就放仓库外的项目目录。`/tmp` 只放可丢弃的中间产物。

## 品味

- 复杂度放在适配器边界：核心逻辑保持纯，UI 保持笨。功能写成 service，传输层（RPC handler、HTTP route、MCP tool）只解码输入、调用一个 service 方法、映射错误。
- 类型靠推断，`any` 是敌人。
- 注释只写代码表达不了的约束、外部怪癖或不变量，能一行就一行，最多四行；名字和签名、步骤、历史、刚做的修复留给 PR。
- UI 组件库的组件自己管外观：选 `variant` 或 `size`，不用 `className` 改样式。通用外观加成新 variant，功能专属外观留在该功能的组件里；宽度、flex、margin、position 写在父级。
- React effect 只用来和 React 外部同步：能推导的在 render 里推导，动作放进事件处理函数；真实的生命周期工作也不藏进 ref 或 store 来回避 effect。
- 动画只在状态变化时播放、播完即停；持续重绘在高刷新率屏幕上会占满 GPU。
- 没有真实用户的项目：直接换成最简单的实现并更新全部调用方，不做兼容、迁移或旧实现备用。
- dev 模式和只给维护者用的功能，安全做到够用即可。
